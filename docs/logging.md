# Логирование и метрики

Для текстовых сообщений используйте `taei.logging` — общий API проекта. Не добавляйте второй sink Loguru или конкурирующий проектный wrapper.

- Конфигурацию задавайте в Hydra под `logging`; приложение настраивает логирование после композиции Hydra и до сообщений. Для обычного mapping или теста Hydra не требуется.
- `configure_logging(config=cfg)` принимает полную конфигурацию; `configure_logging(level=...)` сохраняет возможность явно указать уровень. Явный аргумент `level` имеет приоритет над `logging.level`, затем используются `TAEI_LOG_LEVEL` и `INFO` по умолчанию. `logging.markup: false` отключает разметку Rich.
- `rich_console()` создаёт Rich-консоль, `progress()` — низкоуровневый Rich-индикатор. Для длительных матричных запусков и калибровки используйте `experiment_progress(total, label)`: `stage()` сообщает только наблюдаемый этап, `advance(outcome)` — только реально завершённую единицу работы (попытку или профиль калибровки).
- На интерактивном TTY индикатор показывает число завершённых единиц работы из общего числа, текущий этап, прошедшее время и оценку оставшегося времени по завершённым единицам. В датасетном запуске единица — реальная попытка, в калибровке — профиль (minimal или detailed). Это не процент GPU-работы: ход генерации внутри непрозрачного запуска не оценивается. До первой завершённой единицы ETA неизвестна.
- Для обычного pipe/CI, `NO_COLOR` и `TERM=dumb` вывод ограничен строками начала, смены этапа, завершения единицы работы и итога; анимация и ANSI-коды отключены. Периодические сообщения включаются только для detached-запуска, как описано ниже.
- Процедура эксперимента возвращает итоговый JSON-сериализуемый словарь метрик. Runtime вызывает общий `taei.metrics.log_metrics` и сохраняет полный результат один раз в `results.json`; консоль получает одну компактную строку `metrics: ...`, подробные пары ключ/значение доступны на DEBUG. Не вызывайте `log_metrics` повторно для того же итогового словаря в скрипте эксперимента.
- Вызывайте `log_metrics` из процедуры только для отдельных промежуточных сообщений метрик, когда это действительно нужно; не дублируйте форматирование и отправку метрик.
- Жизненный цикл запуска — вызов процедуры и запись результата — принадлежит общему runtime (`taei.runtime`), а не logging helper. Экспериментальный скрипт задаёт процедуру, возвращает итоговые метрики и передаёт её runtime.

Не печатайте и не добавляйте учётные данные или другие секреты в сообщения, конфигурационные дампы, результаты, общие YAML и документацию.

## Файлы журнала запуска

При запуске с `--detach` launcher автоматически включает текстовый прогрессбар
в `stderr.log`: `[######------------------] 12/48 (25.0%)`, прошедшее время,
приблизительный `ETA` и текущий этап. Строка дописывается при смене этапа,
завершении попытки и каждые 30 секунд ожидания; ANSI-коды и перерисовка строки
не используются, поэтому вывод читается через `tail -f`. До первой завершённой
попытки выводится `ETA~unknown`; затем оценка считается по средней длительности
завершённых попыток и включает их загрузку модели/подготовку. Это доля завершённых
попыток, не процент GPU-работы или успешности. Launcher также включает
небуферизованный Python-вывод дочернего процесса. Уже работающие процессы
не меняют формат вывода до перезапуска с обновлённым кодом.

После каждой попытки dataset entrypoint дополнительно пишет в журнал `run`,
`attempt`, `status` и путь артефактов. Для ошибки указываются этап, тип
исключения и последняя доступная позиция traceback. CUDA OOM выделяется явно;
прочие произвольные сообщения исключений в общий лог не копируются, чтобы не
вывести возможные секреты. Полная причина находится в `traceback.txt` либо
`runs.json` по указанному пути. `success` означает успешное выполнение попытки,
а не подтверждение качества датасета: валидация здесь может быть отключена.
Ошибки супервизора, включая timeout, логируются отдельно и не подавляются.

Runtime настраивает локальный захват при входе в `run_experiment`; для каждого запуска файлы находятся в его Hydra-каталоге:

```text
outputs/<experiment.name>/<каталог-запуска>/
├── config.yaml
├── run.log       # объединённые захваченные console stdout/stderr
├── hydra.log     # файл журнала Hydra/stdlogging
└── logs.zip      # архив только журналов верхнего уровня
```

`run.log` пополняется во время выполнения и включает захваченные console stdout/stderr, в том числе вывод унаследованных потоков нативных программ и дочерних процессов. До перенаправления дескрипторов runtime запоминает, были ли исходные потоки TTY: Rich сохраняет live-рендеринг в терминале, хотя сам захват использует relay-pipe. В pipe/CI прогресс остаётся обычным ограниченным текстом. `hydra.log` — отдельный диагностический файл; сообщения могут дублироваться в нём и `run.log`. ZIP содержит `run.log`, `hydra.log` и найденные в каталоге запуска файлы верхнего уровня `*.log`; это не архив полных артефактов, датасетов или подкаталогов.

Разрешённый `config.yaml` записывается перед вызовом процедуры. После закрытия журнала runtime формирует `logs.zip` при успехе, перехваченной ошибке или `KeyboardInterrupt`; при ошибке сохраняется traceback, а запуск всё равно завершается с ошибкой. Runtime дожидается завершения захвата при штатном teardown и использует резервный путь архивации при проблеме с закрытием журнала.

Захват начинается при входе в `run_experiment`: более ранние сообщения и вывод отдельных/отсоединённых процессов, не унаследовавших захватываемые потоки, не гарантированы. Не гарантируется сохранность при принудительном завершении процесса (например, `SIGKILL`) или отключении питания. `run.log` можно читать во время выполнения; после запуска `logs.zip` можно забрать с машины выполнения через SFTP. Архив содержит только журналы, не все результаты эксперимента.
